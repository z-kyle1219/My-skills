# 陌生项目上手（Repo Onboarding）

## 硬约束（先看这八条）

1. **不凭记忆讲项目**：先确认范围，再读代码。
2. **依赖方向必须有代码证据**，不凭目录名或 README 推断。
3. **主链只有一条**，默认 5–8 步，不横向遍历目录。
4. **设计约定 1–3 个**，凑不出来就少写。
5. **关键结论标 `[代码]` / `[文档]` / `[推断]`**。
6. **静态分析不等于已验证**，不许混说。
7. **只读操作可以直接做**；会改变状态的操作先判断副作用，按风险和授权决定——低风险（隔离环境、测试库、只读查询）可直接执行并说明，涉及改文件、写数据、连真实服务或不可逆操作时，必须先取得明确授权。
8. **自测三问不给答案**，等用户答完再纠正。

## 一、目标

陌生仓库最大的问题不是代码太多，而是缺乏边界感：不知道从哪里进入，不知道各个模块负责什么，也不知道一段功能如何从入口一路执行到最终结果。

本 Skill 不带用户通读仓库，而是通过一条**纵切线**建立项目认知。

纵切线：选一个具体的用户行为或系统行为，从入口开始，沿实际调用关系追到最终输出，理解模块如何协作、数据如何流动。

完成后，用户应能独立回答：

1. 项目从哪里进入？如何运行？
2. 核心模块分别负责什么？彼此如何依赖？
3. 一个具体操作如何执行？经过哪些模块？
4. 数据在调用过程中如何传递和变化？
5. 要修改某个行为，从哪里入手？会影响哪些部分？
6. 如何验证自己的理解和修改？

**默认产物**（按目标取用，不是每次都全出）：≤10 行目录地图、一条完整调用链、核心模块依赖方向与职责边界、1–3 个项目特有约定、值得动手观察或修改的位置、可执行的验证任务、分级待查清单。

**不做什么**：完整文件清单、逐行讲解整个项目、通用语法教学、与当前目标无关的技术栈百科、凭目录名／文件名／README 推测架构、为填满模板而补水内容。

## 二、触发条件与边界

### 适用场景

- 刚 clone 一个陌生项目，想知道从哪里开始读。
- 想学习 GitHub 上的开源项目。
- 接手别人开发的项目，需要建立整体认知。
- 想理解项目中某个已有功能的执行流程。
- 准备在陌生项目中开发功能或提交 PR，需要先了解现有结构。

### 不适用场景

- 已完成某项功能，想复盘本次改动 → `feature-recap`。
- 已明确要开发什么新功能，想规划实施方案 → `feature-kickoff`。
- 只想安装或运行项目 → 走「只想跑起来」分支。
- 只想了解软件怎么用 → 优先查 README 和使用文档，直接回答，不进入代码上手流程。
- 只问一个孤立的技术知识点 → 直接回答。
- 只想评价项目质量、技术选型或发展前景 → 按评价目标单独分析。

### 该怎么判断用哪个 Skill

不要用「有没有 commit」一刀切，看用户当前想解决什么问题。

| 用户想做的事 | 使用 |
|---|---|
| 理解陌生项目整体结构 | repo-onboarding |
| 理解项目中已有功能的执行流程 | repo-onboarding |
| 复盘某次已经完成的改动 | feature-recap |
| 规划一个准备开发的新功能 | feature-kickoff |
| 有 commit，但想了解整个项目 | repo-onboarding |
| 有未提交改动，想理解当前项目 | repo-onboarding，必要时参考 diff |

判断原则：**用户想理解现有项目，还是复盘已经发生的改动？**

commit 和 diff 是理解改动的重要证据，但不是触发 Skill 的唯一条件。

## 三、执行流程

八个阶段（第零步至第七步）不是必须全部走过的流水线，而是可组合的积木。第零步确认上下文，第一步选路线，其余按需执行。

### 第零步：确认上下文

确认三件事，只补缺失的部分：

1. **项目位置**：当前工作区、仓库路径或用户提供的远程仓库。
2. **学习目标**：了解概况 / 理解架构 / 学某条功能链路 / 准备修改或提交 PR。
3. **技术熟悉度**：对项目使用的语言、框架和相关技术是否熟悉。

执行要求：

- 先利用已有对话、项目文档和历史上下文，不重复询问。
- 只问影响路线的缺失信息。
- 用户已指定目标就不再确认。
- 熟悉度可以边做边调整。
- 不为了集齐信息而卡住分析。

#### 特殊分支：只想跑起来

只给五样：

1. 环境和依赖要求。
2. 最小安装命令。
3. 最小启动命令。
4. 正常运行时应该看到什么。
5. 两个最常见的启动失败原因。

命令以项目实际配置为依据（README、`package.json`、`pyproject.toml`、`requirements.txt`、`Dockerfile`），不凭经验编造；环境变量以 `.env.example`、项目文档或实际代码为依据；缺少必要配置就明确告诉用户需要补什么。

执行安装、启动或初始化命令前，先确认它不会改动用户现有文件或数据。可能不可逆的，先说明风险并取得授权。完整判断清单见第七步，不在这里重复。

不展开项目架构和调用链。

### 第一步：按目标选路线

| 用户目标 | 走的阶段 |
|---|---|
| 了解项目概况 | 2 → 3 |
| 学习项目架构 | 2 → 3 → 4（只追接线）→ 5 |
| 学习某个功能链路 | 2 → 3 → 4（追数据变化）→ 6 |
| 准备修改功能 | 2 → 3 → 4 → 5 → 6 |
| 准备提交 PR | 2 → 3 → 4 → 5 → 6 + 贡献约定与相似实现 |

只想跑起来的不进入本表，走第零步的特殊分支。

第七步（验证）按目标执行，通常用于学功能链路、准备修改、准备提 PR。学架构时至少做一次第一层运行验证——没跑过的分层描述只能是推断。

第六步是最终整理方式，不代表必须执行所有分析阶段。按路线裁剪输出，不要为了填模板补充无关内容。

### 第二步：判断规模，划定边界

不要一开始就遍历整个仓库。

**判断复杂度**：不只看文件数，还要看是否存在多个独立应用或服务、多个启动入口、多个数据库或外部服务、消息队列 / 异步任务 / 定时任务、多套技术栈或多个子项目、复杂的权限与事务边界。

**确定边界**：

| 项目情况 | 处理方式 |
|---|---|
| 普通单体项目 | 选一个具体功能，追踪完整链路 |
| Monorepo | 先缩小到一个 app 或 package |
| 微服务项目 | 先选一个服务，不横向展开所有服务 |
| 多入口项目 | 确认本轮目标对应哪个入口 |
| 复杂业务系统 | 选一个用户可感知的具体行为 |
| 多技术栈项目 | 先确定本轮需要理解的技术边界 |

判断标准：**能否在当前范围内合理闭合一条从入口到输出的调用链？** 闭合不了，说明范围可能太大，需要继续缩小。

开始分析前简要说明：本轮准备看什么、为什么选这个范围、哪些内容暂时不看。不为了追求完整而扩大范围。

### 第三步：绘制项目地图（≤10 行）

目标是让用户先知道项目大致由哪些部分组成，本轮该关注哪里。

**优先关注**：项目入口、核心业务模块、数据访问模块、配置与依赖管理、前端页面或 API 路由、测试目录。只展示与本轮目标有关的目录。

**三个锚点**：入口（程序从哪启动、请求从哪进入）、依赖（`package.json` / `pyproject.toml` / `requirements.txt`）、配置（环境变量、数据库连接、运行配置）。按项目实际情况取，不要求每个项目都有同一种文件。

**依赖方向必须有证据**：

```text
API 路由 → 业务服务 → 数据访问层 → PostgreSQL
```

这只是示意。真实关系要由 import / require、函数调用、依赖注入、实例创建、配置引用、实际请求或任务关系确认。

**不能仅凭目录名称判断。** 依赖方向尚未确认时标为推断，不当事实；目录结构与实际调用不一致时，以实际调用关系为准。

**默认不展开**：`node_modules`、`dist` / `build`、`vendor`、自动生成代码、自动生成的 API 文档、大型静态资源、与目标无关的历史迁移。

三个例外：

- 测试代码不是无关代码，关键行为要查对应测试并与实现交叉核对。
- 学数据库结构或数据演变时迁移脚本不能排除。
- 目标涉及构建、部署、打包时相关配置不能排除。

目录名看不懂就读该目录的 README 或 index 文件，不凭名字猜。

### 第四步：切一条纵切线

这是整个 Skill 的核心。选一个具体行为，从入口沿实际调用关系追到最终输出。

**选切入点**：用户指定了功能就直接用。没指定就给 2–3 个有代表性的候选让用户选。优先用户可感知的行为：点一个按钮、发一次 HTTP 请求、执行一条命令、增删改查一条数据、上传下载文件、执行一次定时任务。不要随便挑一个复杂但与目标无关的内部函数。

**五条阅读纪律**

**一、每层先只看接线。**

先读函数签名、输入参数、参数如何传递、返回值、下一步调了谁。函数体先当黑盒，不一开始逐行分析实现细节。

**二、追踪跨层数据变化。**

```text
用户输入 → HTTP Request → JSON → Pydantic Model
→ 业务函数 → 数据库记录 → JSON Response
```

关注数据在哪里被创建、校验、转换、持久化、包装成最终输出。不要只记调用关系却忽略数据本身的变化；没有发生转换的环节不必强行描述。

**三、遇到陌生第三方库，先记录，不要陷入源码。**

先确认项目调了它什么接口、传入参数和返回值是什么、它在当前链路的作用；只有理解主链必须知道其行为时，才查官方文档或最小示例。不要因为一个库不熟就把整个分析拖进源码阅读。

**四、遇到关键问题，可以原地下沉一层。**

只看签名和调用关系无法解释主链关键行为时——为什么在这里校验、为什么捕获异常、为什么转换格式、为什么需要事务、为什么用异步——进入该函数看必要实现。目的是回答当前主链问题，看完回主链，不递归展开所有内部调用，不把一次上手变成无限源码考古。

**五、识别重要边界。**

前后端边界、HTTP 请求与响应边界、业务逻辑与数据访问边界、本地模块与外部服务边界、同步与异步边界、权限 / 事务 / 异常处理边界。这些边界可能比普通中间函数更重要，不要为了缩短链路而省略。

**主链记录格式（两档）**

默认紧凑，一步两行：

```text
1. 用户点"生成播报" → popup.py:on_generate()
   输入：当前日期 ｜ 处理：拼请求、读缓存键 ｜ 输出：weather dict
```

只有出现跨层边界或数据转换的步骤，才展开成：

```text
文件路径：函数名
输入：
处理：
输出：
下一步：
```

**长度控制**：理想 5–8 步。超过 8 步，先查是否做了横向阅读、能否合并纯透传步骤；少于 3 步，先查切入点是否太浅、是否漏了关键环节。

但不机械追求步数：

- 简单项目真实只有 2–3 步，就不补不存在的环节。
- 复杂项目即使超过 8 步，也不能为满足数字省略关键处理。
- 权限、事务、数据转换、异常处理、跨服务边界即使看着像中间层，也要保留。

### 第五步：识别项目特有的设计约定

从当前分析范围中挑 1–3 个值得用户理解的约定。不为凑数罗列设计模式，优先选会影响后续阅读、修改、扩展的那些。

| 设计约定 | 需要解释什么 |
|---|---|
| Repository | 数据访问逻辑如何组织，业务代码如何使用它 |
| Service | 业务逻辑放在哪里，为什么不直接写在路由中 |
| 依赖注入 | 依赖如何创建和传递，谁负责管理生命周期 |
| Middleware | 请求进入业务处理前后会经过什么逻辑 |
| Schema / Model 分离 | 请求数据、业务对象、数据库实体如何区分 |
| 统一异常处理 | 错误在哪里被捕获，如何转换成响应 |

每个约定说明三件事：

- **解决什么问题**：为什么项目需要这种组织方式。
- **项目怎么用**：实际代码中的体现。
- **代码在哪**：具体路径和关键函数。

**取证顺序**（回答「现在到底怎么组织」）：

1. **实际代码和调用关系**：确认项目当前怎么实现。重点看模块职责、调用方向、对象创建、数据传递。
2. **测试代码**：辅助确认预期行为、输入输出和边界条件，并与实现交叉核对。
3. **项目自己的文档**：README、CONTRIBUTING、`docs/`、架构说明，了解设计意图。
4. **Git 提交记录和 PR 描述**：了解为什么做出某项决策，按项目可用性取，不要求都有。
5. **目录结构和命名**：最弱的线索，只能辅助找代码，不能作为设计结论。

每种证据都有局限：

- 文档写的是设计意图，不一定代表当前代码实际如此。
- 测试写的是预期行为，不一定覆盖真实运行情况。
- 提交说明解释的是历史决策，不代表当前实现仍然如此。
- **代码的实际行为，是判断当前实现的主要依据。**

**如果用户问的是「为什么这么设计」**：顺序反过来——先看文档和 `git log`（意图只写在那里），再用代码确认这个意图现在是否还成立。

证据不足时标 `[推断]`，不写成事实；不凭类名、目录名贴设计模式标签。

项目没有明显约定就少写甚至不写——「这个项目没有明显约定，逻辑基本写在路由里」本身是有价值的结论。

### 第六步：整理分析结果

按目标裁剪，不要让所有路线都输出同一份长报告。

**1. 项目定位**：解决什么问题、主要技术、本轮分析范围。结论要有代码或文档依据。

**2. 项目地图**：≤10 行，核心目录及职责。

**3. 主链**：按上一步的两档格式，标文件路径、关键函数、输入、处理、输出。只了解项目概况时可省略完整主链。

**4. 依赖与设计约定**：核心模块依赖方向 + 1–3 个设计约定。

**5. 从哪里开始动手或观察**：给具体位置，不说「从业务层开始」。

| 想改什么 | 从哪里开始 |
|---|---|
| 接口输入校验 | 对应 Schema / Pydantic Model |
| 业务规则 | 对应 Service 或业务函数 |
| 数据库查询 | 对应 Repository 或 SQL 语句 |
| 页面展示 | 对应组件或模板 |
| 数据表结构 | 模型 + 迁移脚本 + 相关查询 |

同时指出可能受影响的模块和需要关注的测试。

**6. 自测三问**：覆盖入口与调用关系、数据流动与关键处理、修改位置与影响范围。不立即给答案；必须能靠本轮分析回答；不考无关语法或冷门细节。用户答完再判断，答不全先给提示再补充。这三个问题同时是第七步第二层的题目，不要另出一套。

**7. 待查清单**：

- **必须查清**：不懂就无法继续开发或正确理解主链。
- **值得了解**：有助于深入但不影响当前目标。
- **暂时跳过**：与当前目标无关。

不把陌生技术全列为必须查清。

**8. 篇幅**：默认两屏约 60–80 行，按目标增减。超出时按顺序压缩：

1. 设计约定从 3 个减到 1 个。
2. 合并纯透传的主链步骤。
3. 删除与本轮目标无关的目录说明。
4. 待查清单只留真正有价值的。

不可删：本轮分析范围、关键调用链、重要数据变化、关键模块边界、具体动手位置、自测三问。尤其不能把权限、事务、异常处理、数据转换当普通透传步骤删掉。

**9. 结论标记**：

- `[代码]`：由实际代码、调用关系或配置确认。
- `[文档]`：来自 README、官方文档或项目说明，尚未经代码验证。
- `[推断]`：推测，待确认。

不把推断写成事实。

### 第七步：验证理解

不停在「看起来懂了」。分三层，按目标和授权选择执行。

**第一层：运行验证。**

检查启动命令、依赖、环境变量、数据库与外部服务是否可用、正常运行该出现什么现象、常见错误如何定位、相关测试是否存在并能执行。

执行启动、安装、测试或初始化命令前，先判断可能的副作用：

- 是否会创建、修改或删除文件。
- 是否会改动数据库结构或数据。
- 是否会连接真实数据库或外部服务。
- 是否会触发迁移、初始化、清理或其他写入操作。
- 是否会执行额外的安装脚本或子命令。

**不要因为命令名包含 `test`、`dev`、`init` 就默认它安全。**

可能造成不可逆影响、触碰真实数据或超出授权范围的，先解释作用和风险，取得授权后再执行；能隔离就先隔离（临时分支、测试库、只读方式）。

执行了测试就明确报告：跑了什么、是否通过、哪些没跑、有无环境限制。测试通过只说明对应用例通过，不代表全场景没问题。

**第二层：定位验证。**

直接使用第六步的自测三问，不另外设计题目。让用户靠地图和主链自己回答；答错说明对应模块职责或调用关系还没真正理解。答不上来先给定位提示，不直接公布答案。

**第三层：破坏性验证。**

有控制地改变，观察行为是否符合当前理解：

- 临时改局部逻辑看输出变化。
- 绕过某项校验看错误是否仍发生。
- 在测试中模拟异常看如何传播。
- 改一个配置值看哪些模块受影响。

**安全边界：**

1. 先看 `git status`，确认工作区状态。
2. 不覆盖、不撤销、不清理用户已有改动。
3. 只读操作可以直接执行。
4. 建分支、改文件、写操作必须遵守用户的授权范围。
5. **用户只要求阅读和分析时，不主动执行修改实验；提出实验方案，由用户决定是否执行。**
6. 需要修改时，优先临时分支、副本或隔离环境。
7. 优先纯逻辑、局部配置或测试代码。
8. 不主动对真实数据库、生产环境、用户数据、支付系统、外部服务做破坏性操作。
9. 使用测试库时，优先事务回滚或独立测试数据。
10. 有风险的验证改为静态分析、模拟调用或写测试代码。
11. 执行可能改变状态的命令前，先解释作用和影响。

不为了证明理解而制造不必要的风险。

**验证等级（必须区分）**：

- `静态`：只读代码、调用关系和配置得出。
- `已实际执行`：真的运行了项目、测试或受控实验，并观察到结果。

不能把静态分析说成实际验证，不能把文档里的启动说明说成项目已经成功运行。

## 四、边界情况

**没有 README**：优先从依赖管理文件、启动入口、配置文件、路由或命令入口、核心模块、测试代码建立认知；无法确认用途时，明确说明只能根据代码结构推测。

**README 与代码不一致**：以当前代码为主要依据，文档作参考；明确指出文档说了什么、代码做了什么、差异在哪。不静默选择一边。

**多个入口**：不默认只分析一个；先判断目标对应哪个，多个都与目标有关时说明彼此关系。

**缺少测试**：不等于无法验证。可静态追踪调用关系、检查输入输出、跑最小示例、看日志、写临时测试（需授权）；明确标出哪些结论未经测试验证。

**规模过大**：按第二步的表继续缩小，不为了展示分析能力读完整个项目。

**语言或框架不熟**：不把陌生技术当障碍。先解释主链必须理解的概念，用已有知识类比（Python 函数调用类比 JavaScript、普通参数类比依赖注入、SQL 类比 ORM、同步类比异步再讲差异）。只讲当前主链需要的，不展开成技术课。

## 五、讲解要求

1. 先讲项目实际做了什么，再讲为什么这样设计。
2. 术语第一次出现时用一句白话解释，第二次起直接用。
3. 优先结合真实文件路径、函数名和代码片段。
4. 不堆目录名、类名和术语；区分「项目实际如此」和「通常推荐如此」，不把通用最佳实践当项目现状。
5. 复杂概念用具体的业务或代码场景解释。
6. 用户已掌握的基础不重复讲；不为了显得学到很多而引入当前不需要的概念。

本 Skill 的核心是帮用户建立代码阅读能力，不是让用户记住一份架构报告。

## 六、与其他 Skill 协作

- `feature-recap`：复盘一项已完成改动的具体内容、实现过程和设计决策。上手中发现某个已完成改动值得复盘时切过去。
- `feature-kickoff`：针对准备开发的新功能规划实施方案、影响范围和任务拆分。上手完成后可以把本 Skill 的分析结果作为它的输入。

**复用前序分析**：此前做过地图或链路分析可以复用，但先确认是同一个项目、相关文件没有重要变化、旧结论仍适用于当前目标。代码变了就重新检查，不直接沿用。

## 七、自检

### 执行前（可事前判断）

- [ ] 明确了本轮学习目标。
- [ ] 没重复询问已有信息。
- [ ] 按目标选了分析路线。
- [ ] 划定了合理的项目范围。
- [ ] 确认了授权范围（能否改文件、能否跑实验）。

### 执行后（逐项核对）

- [ ] 只展示了与目标有关的目录，地图 ≤10 行。
- [ ] 模块依赖方向有实际证据，不是看目录名猜的。
- [ ] 主链来自真实行为，没有为了凑步数补充环节。
- [ ] 主链通常 5–8 步；偏离时已确认是项目真实复杂度导致，而不是切入点不合理或横向阅读。
- [ ] 关键数据的传递和变化已追踪。
- [ ] 重要模块边界已识别。
- [ ] 没有陷入第三方库源码。
- [ ] 原地下沉只在必要时发生，且没有递归。
- [ ] 输出已按目标裁剪，没有为填模板补内容。
- [ ] 结论区分了代码、文档和推断。
- [ ] 标明了哪些经过实际验证。
- [ ] 执行命令前判断了副作用。
- [ ] 工作区未被破坏，遵守了用户授权。
- [ ] 留下了能检验理解程度的自测问题。

## 最终原则

**不要试图一次性读懂整个仓库，而是通过一条真实的功能链路，逐步建立对项目的认知。**

先知道从哪里进入，再知道经过哪些模块；先理解数据如何流动，再理解每个模块为什么这样设计。

**本轮什么时候结束**：不看讲了多少，看用户能不能独立回答自测三问。答得上，可以收，下一轮换一条链路；答不上，补的是理解，不是篇幅——不要再加新章节。

最终目标不是让 AI 替用户读完代码，而是让用户逐渐具备独立阅读、定位、理解和修改陌生项目的能力。
