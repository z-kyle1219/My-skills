# 交付后复盘（Feature Recap）

## 目标

把一次功能改动从「能跑」变成「我懂了」。

复盘不是逐行解释代码，而是帮用户建立对本次改动的整体认知：

- 这次改动具体做了什么。
- 数据从哪里来，经过哪些处理，最终到哪里。
- 新增或修改的文件分别承担什么职责。
- 哪些函数是理解这次功能的关键。
- 哪些实现细节决定了功能能否正常工作。
- 以后出问题时，应该从哪里开始排查。

最终产物是一份可以直接归档的学习笔记，以及三道用于检验理解程度的自测题。

## 触发条件

### 适用场景

- 新功能已经完成并 commit，用户希望复盘本次改动。
- 用户希望理解某次提交涉及的代码及其运行过程。
- 用户希望把本次功能整理成学习笔记。
- 用户询问本次改动中的某个函数或代码段，希望理解其运行逻辑。

### 不适用场景

- 生成 commit message：使用 `standard-commit`。
- 提交前检查：使用 `pre-commit-checklist`。
- 动手前的方案设计：使用 `feature-kickoff`。
- 总结当天工作、生成项目总结文档等非代码复盘任务。
- 与本次改动无关的知识点提问。

用户只说「总结一下」而对象不明时，先用一句话确认是复盘代码还是总结别的，不要直接按「不适用」沉默跳过，也不要抢跑成完整复盘。

## 完整复盘与轻量模式

根据用户的实际问题选择模式，不要所有问题都套用完整模板。

### 完整复盘

满足以下任一条件时使用：

- 本次改动涉及 2 个及以上文件。
- 本次改动跨越模块边界。
- 虽然只涉及一个文件，但其中存在值得系统理解的复杂业务逻辑（例如同时涉及线程、持久化和界面刷新）。

### 轻量模式

用户只询问单个函数或单段代码，且该代码属于本次改动时使用。要求：

- 围绕目标代码追踪必要的调用关系。
- 解释输入、输出、执行过程和关键原理。
- 不套用完整复盘模板。
- 跳过第五步收尾。

轻量模式至少检查三处：

1. 目标函数本身。
2. 谁会调用它，以及在什么情况下调用。
3. 它调用了哪些关键函数，以及这些函数承担什么职责。

不要只看函数体就直接解释。函数本身的逻辑可能很简单，但真正决定它何时执行、为什么执行的，往往是调用方。

如果用户询问的代码与本次改动无关，直接正常回答，不启动复盘流程。

两种模式都必须基于实际项目代码，不凭记忆解释。

## 第一步：确认改动范围

必须先通过 Git 确认实际改动，再阅读代码。不能仅凭 commit message、用户描述或自己的记忆判断改动内容。

### 1. 确认目标提交

- 用户指定了 commit 或提交区间：按用户指定的范围复盘。
- 用户没有指定：查看最近提交，结合提交说明和文件变更，给出 2–3 个候选提交，让用户确认。
- 工作区干净不代表最近一次 commit 就是本次目标。
- 用户明确要求复盘尚未 commit 的改动：可以只读检查工作区，并说明当前范围可能继续变化。

### 2. 确认具体改动

使用只读 Git 命令：

```bash
git log -1 --stat <commit>              # 改动概况
git show --format=fuller --stat <commit>  # 提交信息 + 文件范围
git diff <commit>^ <commit> -- <file>     # 单文件的真实改动
```

对合并提交或多提交功能，根据实际情况确定比较基准，不要机械使用 `^`。

**必须落到具体文件列表。** 文件统计只能确定范围，不能代替代码理解——不要只看提交说明和 `--stat` 就开始复盘。

读代码要有预算，不要把整个文件或整个项目读一遍：

- 读核心函数所在的**完整函数**，而不是整个文件。
- 每个核心函数看三处：它自己、谁调用它（可用 `grep` 找引用）、它调用了什么。
- 超出这个范围还需要的上下文，先判断「不理解它就讲不清数据流吗」，不是就跳过。

### 3. 确认运行链路

范围确定后，只复盘本次 diff 触及的链路。

- 本次改动接入既有链路（例如新接口挂到原有数据流上）：一句话说明接口点，不展开讲整个旧系统。
- 涉及多个独立功能：不要强行拼成一条数据流，先分别明确范围。
- 读不到仓库或目标提交不存在：明确说明，让用户提供仓库或代码，不编造改动内容。

所有 Git 操作保持只读：不切换分支、不修改文件、不执行 add、commit、reset 等会改变仓库状态的操作。

## 第二步：按固定结构输出

完整复盘严格照下面的结构写，不要自由发挥。

````markdown
## 这次改了什么
（3 行以内，白话，说清"现在能做什么了"）

## 数据流
（一条主链，5–8 步，每步写成「动作 → 文件:函数」；只画一条，不画分支图）

## 第一层：结构
（只列新增的文件、职责发生变化的文件，每个一行：职责 + 以后改相关功能从哪里进。
 职责没变的文件不列）

## 第二层：核心函数
（最多 3 个。每个按：签名 / 输入从哪来 / 返回或副作用 / 谁调用它 / 为什么需要它）

## 第三层：关键实现
（只写本次 diff 里真实存在的，最多 4 条。例如：这段跑在哪个线程、
 锁保护的是什么、失败走哪条分支、数据存到哪、超时和重试怎么设的）

## 为什么这样设计
（最多 2 处，只解释影响后续改动的重要决策）

## 你该留意的风险点
（1–3 条，只列有实际代码依据的，每条写触发条件、可能现象、排查入口）

## 自测三问
（3 道题，不在这里给答案）
````

### 篇幅规则

整体优先控制在两屏左右。超出时**按固定顺序压缩，不要平均砍**：

1. 先删「第一层：结构」里职责没变的文件。
2. 再把「第二层」压到 2 个函数。
3. 再把「为什么这样设计」压到 1 处。
4. 最后才动「第三层」，删到 2 条。

「数据流」和「第三层：关键实现」是本次改动不可压缩的部分。

允许超出两屏的唯一理由：本次改动真实存在多线程、异步回调或跨模块数据传递，压缩会导致执行顺序讲错。除此之外，不因为「想讲全」而扩展。

### 输出纪律

- **核心函数最多 3 个。** 挑选标准：核心业务逻辑、模块之间的连接点、重要状态修改、数据持久化或外部交互。挑不出来，说明这次改动太散，这点也值得直接告诉用户。
- 每个函数不超过 5 行解释。重点讲输入、输出、调用关系和存在的原因。
- 不逐行解释简单代码。判断标准：一行代码读出来就是它字面意思，跳过。
- 第三层不要罗列通用概念。这个项目里没有异步任务、没有数据迁移，就不要提。
- 不适用的小节**直接删掉**，不留空标题，也不写「不适用」凑结构。
- 数据流只展示主要执行路径，但必须保留真实的线程切换、异步等待、事件回调和队列传递关系。不能为了线性好看，把异步执行描述成同步执行。
- 文件职责只写本次涉及的文件，不扩展成整个项目的文件介绍。

## 第三步：解释「为什么」，但只挑两处

用户真正想知道的是「AI 为什么这么写」。全部解释会把篇幅撑爆，所以**最多挑 2 处有取舍的地方**，每处按这个格式写：

- 它做了什么选择。
- 为什么这样选，当前实现受到什么约束。
- 另一个可行方案是什么，为什么没采用。

只挑影响后续改动的决策：数据放在哪里、状态由哪个模块持有、同步还是异步、为什么用这种数据结构、为什么这样划分模块或接口边界、为什么选这个第三方库或 API。纯代码风格差异不占名额。

**取证顺序（重要）：**

1. commit message、分支名、项目文档——经常直接写着当时的意图。规范化的 commit 会标明这次是 feat / fix / refactor，比从代码反推可靠得多。
2. 改动前后的对照——diff 从前是什么、现在变成什么，能看出被替换掉的方案。
3. 代码本身——只能证明「这么做」，通常不能证明「为什么这么做」。

diff 能证明做了什么，不一定能证明当时为什么这么做。无法确认原始意图时，标注「从当前实现推断」，不把推测写成已确认的设计原因。**不要为了填满两处而编造设计决策**——找不到第二个有依据的，就只写一个。

## 第四步：风险分析与自测

### 风险分析

只列本次改动中有实际代码依据的风险，不把复盘变成通用代码审查。每条包含：

- 触发条件：什么情况下会出问题。
- 可能现象：用户会看到什么异常。
- 排查入口：优先检查哪个文件、函数或调用环节。

区分已确认的问题与潜在风险，不把所有可能性都描述成当前代码存在的 Bug。没有足够依据就不列，不为凑满条数制造问题。

### 自测题

给 3 道题，覆盖三个不同层次，问题必须来自本次真实改动：

1. **定位题**：「要给这个功能加 X，你会先改哪个文件？」
2. **因果题**：「这里为什么加锁」「为什么先写库再更新界面？」
3. **排查题**：「如果用户反馈 Y 失效了，你从哪一步开始查？」

难度以用户能结合刚才的复盘思考为准。**同一轮里不要给答案。**

等用户回答，再逐条纠正：

- 答对的明确确认，并说明正确在哪里。
- 答错或部分正确的，指出偏差、补齐遗漏的关键环节。
- **答对了但停在表层的，追一个问题：**「那如果改成 X 会怎样？」一次只追一个，不要连问。

这一步是整个复盘里最值钱的部分，不要跳过，也不要自问自答。如果用户跳过答题直接进入下一个任务，不追问，也不假装他答过。

## 第五步：收尾（不写进复盘正文）

复盘结束后，在对话里另起两段。它们属于下一次的待办，不是本次复盘的内容，不要并进上面的模板。轻量模式跳过这两项。

### 1. 待补原理清单

本次改动中碰到但用户可能还没吃透的概念，1–3 条。每条标注：

- 概念是什么。
- 什么时候会真正卡住。
- 建议先理解到什么程度。

优先选与本次改动直接相关的知识，不扩展成通用学习路线。可以直接给一段可粘贴的 Markdown，方便存进笔记。

### 2. 一个动手任务

从本次改动中挑一个边界清晰的小任务，帮用户从「读得懂」过渡到「改得动」。优先选择：

- 闭卷重写一个核心函数。
- 给现有函数增加一种输入或边界情况。
- 修改一个小功能，并接入现有数据流。
- 为一个关键函数补充测试。

通常控制在 20–50 行；实际逻辑更简单就不必凑行数。**不要直接给完整实现**，只说明任务目标、涉及文件和验收标准。

## 用词要求

用户是零基础起步，术语不用等于降低专业性，但必须可读：

- 术语第一次出现时用一句大白话括注，例如「幂等（同样的请求发两次，结果一样）」。
- 第二次起直接用术语，不要反复解释。
- 宁可换一种说法，也不要用一串没解释的术语把结论包起来。

## 与其他 Skill 的关系

- `feature-kickoff`：动手前规划。本 Skill 与它首尾呼应，但不重复它的影响面和风险预判——这里只讲**已经发生**的改动。
- `pre-commit-checklist`：交付前检查。本 Skill 在功能完成并 commit 后执行，不替代提交前的检查职责。
- `standard-commit`：commit message。本 Skill 不生成 commit message，但会读它产出的 message 作为设计意图的证据。

## 快速自检

- [ ] 目标提交来自 Git 或用户明确指定，不是凭记忆。
- [ ] 已确认具体文件列表，并阅读真实 diff。
- [ ] 读代码控制在「核心函数 + 调用方 + 被调用方」，没有通读整个文件或项目。
- [ ] 核心函数 ≤ 3 个，每个 ≤ 5 行解释。
- [ ] 第一层只列了新增和职责变化的文件。
- [ ] 数据流只有一条主要路径，保留了真实的异步和线程关系。
- [ ] 第三层的每一条都能在本次 diff 或相关实际代码中找到依据。
- [ ] 设计决策不超过 2 处，取证顺序正确，事实与推断已区分。
- [ ] 风险点有实际代码依据，没有为凑数制造问题。
- [ ] 出了 3 道自测题，没有同时给答案，纠正时对答对但表层的追问了一层。
- [ ] 待补原理和动手任务在模板之外，轻量模式下已跳过。
- [ ] 没有为凑结构保留空小节。
- [ ] 所有 Git 操作均为只读，没有改变仓库状态。
