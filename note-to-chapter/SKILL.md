# 原始笔记 → 知识章节（保真优先）

## 目标

把用户手写的碎片笔记（文本 + 截图）变成能长期读的章节，同时**不改变用户的原意**。

章节好看是第二位的。第一位是：三个月后回头看，每一句都能说清「这是我自己写的」还是「这是 AI 补的，依据在哪」。

## 触发条件

### 适用场景

- 用户上传文本笔记 / 截图，希望整理成知识点、章节、网页页面。
- 用户要求"润色""排版""整理""整合成图文笔记"。
- 已有章节需要补题、补图、补小节。

### 不适用场景

- 只问某个知识点对不对：直接回答。
- 复盘已完成的代码改动：`feature-recap`。
- 生成提交信息：`standard-commit`。
- 动手前的方案设计：`feature-kickoff`。

## 核心原则（六条，不可让步）

1. **不改写原则**：用户的句子只做结构处理（加标题、拆分点、转表格、给关键词加粗），**不改措辞**。
   - 尤其是「定义、下标边界、判空判满条件、复杂度、算法步骤」这类**可判对错**的句子，必须逐字保留。
   - 如果确实必须改（原句与已知事实冲突），先单独列出，说明冲突在哪，让用户决定，**不要默默改掉**。

2. **三层来源标注**：每一段都要能回答「谁说的」。
   - **原文**：用户笔记 / 截图里的内容。
   - **补充**：我加的"为什么、怎么记、易错"，必须带依据（`依据：<截图> / <教材某节> / 推断`）。
   - **待确认**：不确定的一律标 `待确认`，不合并、不删、不替用户拍板。

3. **先骨架，后正文**：第一轮只出知识点清单（小节标题 + 一句用户原话），确认后再写文件。
   错误在骨架阶段拦截，比在成稿里逐句核对便宜得多。

4. **截图是一等来源**：图片里的表格、例题、颜色标注都要真正读出来，并**用文字/表格复述一遍**——图片不便检索、不便复制、考试时也带不进去。

5. **禁止绝对化**：`所有 / 永远 / 一定 / 唯一 / 必然` 是红旗词。除非原文里就有，否则不写。

6. **交付闸门**：润色/修改完成的正文，**先在对话里完整展示给用户看**，等用户确认无误后，才写入站点文件（`notes/*.md`、`index.json`、样式）或提交上传。
   - 未经确认不落盘，也不"先传上去再说"。
   - 用户提出修改后，重新展示改动处，再次确认。
   - 确认方式可以是「确认无误」「可以上传」，也可以是指出问题；用户未回应即视为未确认。

## 为什么这样做

润色本身不是问题，**"重写"才是**：句子换成了我的表述，来源却从"用户的材料"变成了"我的通用印象"。一旦两者冲突，错的是我，但书面语读起来像是用户自己写的——这才是最难发现的地方。

## 步骤

### 第一步：读全材料，先不做判断

- 找到本次材料：文本笔记、截图、已有 md、相关题解。
- 截图必须实际打开看，逐行读表格、逐步读例题、注意颜色/加粗标了哪一步。
- 顺手记住用户的语言习惯（口语、比喻、缩写、编号方式），后面尽量沿用他的说法，而不是换成更"标准"的表述。

### 第二步：出骨架清单（不写正文）

只输出一张表，不生成任何文件：

| 小节 | 一句话（用原文措辞，不加解释） | 来源 |
| --- | --- | --- |
| 顺序栈 | 由一个数组 data + 一个指针 top 表示 | 文本笔记 |
| 中缀转后缀 | 遇到字母或数字：直接放进后缀表达式，不入栈 | 文本笔记 |

同时列出**我打算补充的内容**（一句话一条），以及**我判断有疑问、需要用户确认的点**。

等用户点头/修正，再进入第三步。

### 第三步：分级扩写

- 原文部分：原样搬，只加层级和格式。
- 补充部分：只写"为什么这样设计""怎么记""易错在哪"，每条带依据标签。
- 灰区：写成 `> 待确认：……` 单独一行，不并入正文结论。
- **本轮产出直接呈现在对话里，不写文件**（见核心原则 6）。

### 第四步：图片编排

- 图片放在**对应规则/概念的正下方**，不要飘在章节末尾。
- 多图按「原理演示 → 完整例题」排序，不要按上传顺序。
- 每张图配图注：这张图在讲哪一步、看哪个角落。
- 图内信息用表格复述（长表格照抄行列结构即可）。
- 若图片里的例题在一个文档出现两次（讲义版 + 详细版），说明它们的差别，不要当成两张重复图。

### 第五步：交付对照清单

正文交付时，附一张表：

| 用户原句 | 我的表述 | 依据 |
| --- | --- | --- |
| 一端插入，另一端删除 | 一端进、另一端出 | 原文（仅句法调整） |
| （无） | 每个元素最多被搬两次 | 推断 |

只有「推断」那几行需要用户逐条核。若改动了原句，单独列一节说明改了什么、为什么改。

### 第六步：站点接入（静态站场景）

**前置条件：用户已确认上一步的正文。** 未确认不动这一步。

1. 新建 `notes/<slug>.md`，frontmatter 至少 `title`，可选 `tags / subtitle / difficulty / status`。
2. `notes/index.json` 登记，**放进与知识点同一个分组**，题解跟在知识点后面，编号连续（如 `03` → `03.1`），保持"一章"的观感。
3. 图片引用路径写清，配 `figcaption`。
4. 落盘后告诉用户怎么本地预览 → 用户验收 → 再谈 commit（交给 `standard-commit`）。

## 输出纪律

- 不逐句解释简单代码；判断标准是一行读出来就是字面意思。
- 术语第一次出现给一句大白话括注，第二次起直接用。
- 小节顺序默认沿用用户笔记的顺序；若必须调整（例如把"栈与递归"从队列后面挪回栈），单独说明理由。
- 不用为了句子对称牺牲准确性。**对称是好句子的敌人**（见下）。

## 常见失败模式（都真实发生过）

| 失败模式 | 真实例子 | 改法 |
| --- | --- | --- |
| 为对称牺牲准确 | 「栈和队列…**都只允许在一端动**，区别只在于动的是哪一端」——队列明明两端都在动 | 拆成两句分述，不要合并成一个对称句 |
| 把建议升级成断言 | 「**所有**栈的题、**所有**栈的 bug，几乎都出在这两个判断上」 | 降级为"大多"，或直接保留原文的"要考虑" |
| 用比喻替代机制 | 「`front` 永远**追着** `rear` 跑」——循环队列里两个下标都在绕圈 | 直接写清下标怎么移动、有效区间是哪一段 |

## 快速自检

- [ ] 每一句都能回答"谁说的"（原文 / 补充 / 待确认）
- [ ] 定义、边界条件、复杂度、算法步骤与原文逐字一致
- [ ] 所有 `所有/永远/一定/唯一` 都能在原文里找到出处
- [ ] 图片在对应规则下方，且有图注，图内信息已用表格复述
- [ ] 补充内容都带依据标签，推断已明确写"推断"
- [ ] 交付时附了对照清单
- [ ] 不确定项标了「待确认」，而不是被悄悄删掉或合并
- [ ] 站点接入：md + index.json 登记 + 图片 + 同组编排
- [ ] **正文已完整展示并经用户确认，才动文件**（未确认不落盘、不上传）
- [ ] 单轮输出没有出现"先改完再说"的静默改写
