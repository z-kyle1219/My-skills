# 提交前检查（Pre-commit Checklist）

## 目标

在代码提交前，按照项目实际情况完成一轮交付检查，尽量保证：

- 代码能够通过必要的自检。
- 相关测试已经运行，结果明确。
- 项目结构文档与实际代码保持一致。
- Git 提交范围清晰，没有误提交隐私文件、密钥或生成物。
- Commit message 符合项目现有风格，或遵循 Conventional Commits 规范。

本 Skill 负责组织提交前的检查流程，不负责替用户执行 commit 或 push。

项目已有的 AGENTS.md、README、开发文档和配置文件优先级更高。检查命令、测试方式和项目规则应以实际项目为准，不要假定所有项目都使用相同的技术栈或目录结构。

## 什么时候使用

在以下场景使用：

- 用户明确表示准备提交代码，需要进行提交前检查。
- 用户要求检查当前改动能不能 commit。
- 用户要求进行开发收尾，确认代码、测试和文档是否完整。
- 用户明确要求检查结构文档、隐私文件或提交范围。

如果用户只说"做完了"、"好了"、"可以了"等，但没有明确的开发收尾或提交语境，不要仅凭这句话自动启动完整检查。

如果无法确定用户是想检查代码、准备提交，还是直接执行其他操作，应先询问。

## 检查流程

按照下面的顺序执行。根据项目实际情况决定具体命令，不要为了完成清单而机械执行不适用的步骤。

### 1. 语法与导入链自检

先查看项目的 AGENTS.md、README 和配置文件，确认项目已有的语法检查、导入检查或其他快速自检方式。

例如，Python 项目可能存在：

`uv run python _compile_check.py`

如果项目已有这类检查脚本，优先使用项目规定的命令。

检查时注意：

- 存在明确的 FAIL、IMPORT-ERR 或其他错误时，先定位问题。
- 如果错误由本次改动引起，应优先修复，再重新检查。
- 如果错误来自已有问题或环境问题，应记录具体原因，不要直接归因于本次改动。
- 如果项目没有相关脚本，也没有必要单独执行的语法检查，不必为了清单而创建新脚本。

**没有执行检查，不等于检查通过。**

### 2. 运行测试

根据项目现有的测试框架和配置，确定需要运行的测试命令。

例如，Python 项目可能使用：

`uv run pytest`

其他项目应使用自己的测试命令，不要直接套用上述命令。

检查时注意：

- 优先运行与本次改动相关的测试。
- 如果项目要求运行完整测试集，应按照项目要求执行。
- 测试失败时，区分本次改动引入的问题、已有失败、环境问题和依赖缺失。
- 如果失败明确由本次改动引起，应优先修复并重新运行测试。
- 如果测试无法运行，应说明具体原因以及尚未验证的部分。
- 不要为了让测试通过而擅自修改无关代码或删除原有测试。

如果项目没有测试，或当前环境无法运行测试，应如实记录，不要把未运行的测试描述为通过。

### 3. 检查结构文档是否需要同步

检查本次改动是否影响项目结构、模块职责、数据结构或开发说明。

例如：

- 新增、删除或重命名模块。
- 调整目录结构或模块之间的依赖关系。
- 修改数据库表结构或重要的数据模型。
- 修改项目入口、主要运行流程或关键配置方式。
- 原有文档中的描述已经与实际代码不一致。

如果项目有 `PROJECT_STRUCTURE.md`、架构说明或其他相关文档，应检查是否需要同步更新。

判断标准：

**如果改动完成后，原有结构文档中有任何一句话不再准确，就应该考虑更新。**

如果只是修改局部业务逻辑，且没有影响文档描述的内容，通常不需要更新结构文档。

如果项目没有结构文档，也没有明确的文档要求，不要为了完成检查而强行创建新文档。

更新文档后，应再次检查文档描述是否与实际代码一致。

### 4. 检查 Git 状态、实际改动与提交范围

先确认当前分支和工作区状态，再检查本次准备提交的具体内容。

至少检查以下信息：

`git status --short`

`git diff --stat`

`git diff --cached --stat`

其中：

- `git status --short`：查看已修改、已暂存、未跟踪的文件。
- `git diff --stat`：查看尚未暂存的改动统计。
- `git diff --cached --stat`：查看已经暂存的改动统计。

注意：**diff --stat 只能显示改动统计，不能代替对实际代码内容的检查。**

因此，还需要根据当前状态检查具体差异：

- 使用 `git diff` 查看尚未暂存的代码改动。
- 使用 `git diff --cached` 查看已经暂存、实际准备提交的改动。
- 检查未跟踪文件的名称，必要时查看其具体内容。
- 如果存在删除、重命名、二进制文件或其他无法通过普通 diff 充分展示的内容，应根据实际情况进一步确认。

重点检查以下问题：

- 是否包含与本次功能无关的改动。
- 是否有调试代码、临时文件或不应该提交的生成物。
- 是否遗漏了本次功能所需的文件。
- 是否有不应该提交的文件已经进入暂存区。
- 暂存区中的内容是否与用户准备提交的功能一致。

不要只看文件数量或改动行数就判断提交范围正确。

### 5. 检查隐私文件与密钥

检查本次改动中是否包含不适合提交到 Git 仓库的文件或内容。

重点关注：

- `.env`、本地配置文件以及其他可能包含环境变量的文件。
- API Key、Access Token、密码、私钥和数据库连接凭据。
- 本地照片、个人图像及其他不应该公开的个人文件。
- 日志文件、临时文件、缓存、构建产物和本地数据库。
- 其他根据项目规则不应该提交的内容。

不要只根据文件名判断安全性，还应在必要时检查实际 diff 和文件内容。

如果发现疑似密钥、隐私文件或其他不应该提交的内容：

1. 暂停提交前的放行判断。
2. 明确指出可疑文件或内容，以及具体风险。
3. 如果文件已经暂存，提醒用户检查并从暂存区移除不应提交的内容。
4. 如果涉及真实密钥泄漏，应提醒用户评估撤销或轮换密钥的必要性。

不要擅自删除用户文件，也不要在未确认的情况下修改用户的提交范围。

如果没有发现明显问题，可以说明已检查的范围，但不要声称已经保证绝对安全。

### 6. 整理 Commit message

完成前面的检查后，整理一条与实际改动相符的英文 Commit message。

优先遵循项目最近的提交风格。如果项目已经形成稳定的命名习惯，不要为了形式统一而强行改变。

如果项目没有明确的既有规范，则使用 Conventional Commits。

常见格式：

`<type>(<scope>): <subject>`

常见 type：

- `feat`：新增功能。
- `fix`：修复问题。
- `refactor`：重构代码，不改变原有外部行为。
- `test`：新增或修改测试。
- `docs`：修改文档。
- `chore`：维护性改动或其他不属于上述类型的工作。

要求：

- 使用英文。
- Subject 简洁、明确，描述实际完成的改动。
- 优先使用祈使句。
- Subject 末尾不加句号。
- 不要只根据用户最初的需求生成 message，应以最终实际改动为依据。
- 如果一次改动包含多个相互独立的任务，应判断是否需要拆分提交，而不是机械地把所有改动合并成一个 message。

如果需要更详细地分析 Git 改动、选择 type 和 scope，可以遵循 `standard-commit` Skill 中的规则。

如果当前 Agent 支持显式调用其他 Skill，可以调用 `standard-commit`；如果不支持，则直接按照其规则完成，不要假定它一定会自动执行。

### 7. 最终检查结果与交接

完成检查后，简要汇总以下内容：

- 语法或导入自检：通过、失败、未运行或不适用。
- 测试：通过、失败、未运行或不适用，并说明必要原因。
- 结构文档：已同步、不需要更新或仍有待处理项。
- Git 改动：实际涉及的文件及提交范围是否明确。
- 隐私与密钥：检查结果，以及尚未排除的风险。
- Commit message：建议使用的提交信息。
- 待处理问题：如果存在未解决问题，明确说明。

如果检查发现问题，不要为了给出一个完整的清单而把结果标记为全部通过。

如果检查完成且没有阻塞项，可以提供建议的提交信息和命令，例如：

`git commit -m "feat(blog): add article search"`

这里的 message 仅为格式示例，实际使用时必须根据当前项目的真实改动生成。

**默认只提供建议，不执行 `git add`、`git commit` 或 `git push`。**

除非用户明确授权执行对应操作，否则不替用户提交或推送代码。即使检查全部通过，也不能把"检查通过"理解为用户已经授权提交。

## 快速检查清单

- [ ] 已确认项目规则和适用的自检命令。
- [ ] 已运行适用的语法、导入或其他快速检查。
- [ ] 已运行适用的测试，或明确记录未运行的原因。
- [ ] 已检查结构文档是否需要同步。
- [ ] 已检查 Git 状态、未暂存改动和已暂存改动。
- [ ] 已检查未跟踪文件及必要的文件内容。
- [ ] 已检查隐私文件、密钥、日志和生成物。
- [ ] 已确认实际提交范围与本次任务一致。
- [ ] 已根据项目风格整理 Commit message。
- [ ] 未在未经授权的情况下执行 commit 或 push。
