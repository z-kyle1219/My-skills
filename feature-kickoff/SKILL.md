# 功能启动梳理（Feature Kickoff）

## 目标

在开始实现新功能之前，把用户的简要描述整理成一份可执行的启动清单，帮助用户确认：

- 功能的目标、约束和范围是什么。
- 实现要经过哪些关键节点、依赖顺序如何。
- 哪些问题会阻塞正确开工，哪些可采用合理默认。
- 可能影响哪些模块、文件、数据或既有功能。
- 该重点验证哪些主流程、边界和回归风险。
- 建议用什么 Git 分支名。

本 Skill 只做**开发前的分析与规划**。不写实现代码、不改项目文件、不创建/切换分支、不暂存/提交。输出是供用户决策的清单，不是代码。

## 什么时候使用

适用于：用户描述了一个**新功能**，并想先梳理流程/拆步骤/识别风险/规划测试/定分支名。

不要在这些时候触发：

- 修已有 Bug、分析已有代码、代码审查。
- 用户明确要求直接实现，且已有足够清晰可执行的方案（除非同时要求先梳理）。
- 用户只说"做完了""好了"等收尾表达，没有新功能需求。
- 只是在讨论概念或学习，没有实际的新功能规划意图。

判断依据是**用户的实际任务意图**，不是"功能""分支"等关键词。

如果描述过于含糊（如"优化一下"），先用**一个**简短问题确认核心目标，不要一次抛一长串问题。

## 工作原则

### 1. 信息分四类（最重要）

规划类任务最大的失败是**编造文件路径、模块名和现状**。所有输出都必须区分：

- **已确认事实**：能从用户描述、实际读取的项目内容或上下文直接确认。
- **合理假设**：为推进分析暂时采用的默认前提，必须标注。
- **待检查事项**：需进一步看代码/文档/运行结果才能确认的。
- **待用户确认事项**：涉及需求取舍、业务规则、关键实现决策，且无法可靠推断的。

**能自己查的先去查，别把可查的东西推给用户**——"待检查"是给真正需要外部信息的事留的，不是偷懒的出口。无法读取项目文件时，给出有边界的初步分析，受影响处标"待检查"，不要编造。文档与代码冲突时指出冲突，优先核实实现，无法核实时说明不确定性，不要默默选一边。

### 2. 项目约定优先

分支命名、目录结构、测试方式、代码风格、文档规范都优先沿用项目已有约定。本 Skill 的默认值只在**未发现项目约定**时使用；不要为套模板而让项目迁就本 Skill。

### 3. 控制范围

优先规划用户明确提出的功能，不主动扩大本期范围。后续扩展建议可以提，但必须与本期计划分开并标注"后续可选"。

### 4. 提问要有价值

只问会实质影响需求正确性、架构方向、数据设计、接口契约、安全性或实现成本的问题。不影响核心方向的细节，用项目惯例或合理默认推进，并说明所用的假设。

### 5. 分析 ≠ 执行（边界规则）

本 Skill 默认只做分析、检查和规划。允许**只读检查**（读文件、看结构、`git status` / `git branch -a` / `git log` / `git show` / `git diff` / `git remote -v` 等查询）。

**一条硬规则：任何会改变工作区、暂存区、分支或提交历史的操作一律禁止**，包括但不限于创建/删除/切换分支、`git add`/`commit`/`merge`/`rebase`/`reset`/`restore`/`checkout`/`switch`/`stash`/`clean`/`push`/`pull`，以及修改/创建/删除任何项目文件或配置。（子命令清单仅作示例，不追求穷举；拿不准是否只读就当它是写操作，停下来。）命令的参数也须判断，不能因为"通常用于查询"就忽略实际行为。

若某判断必须做被禁止的操作，停在分析阶段，说明无法在只读范围内确认，并给用户可自行执行的下一步。

## 梳理流程

### 第 1 步：理解目标、约束与范围

提取：功能目标（解决什么问题、什么价值）、使用场景与入口、明确约束（技术栈/兼容/性能/安全/明确不做的事）、本期范围、必要假设。用户已说过的不要再问。

### 第 2 步：了解项目上下文

按复杂度适度检查相关文档、代码、配置、接口、测试。判断：功能落在哪些已有模块、有无可复用实现、有无必须遵循的约定、是否与既有实现/文档冲突、哪些已确认哪些待检查。只读相关内容，环境无访问权限时如实说明并标"待检查"。

### 第 3 步：拆分关键节点

拆成有序节点，每个节点是一个**可交付、可验证的中间状态**，不是"写代码""测试一下"这类笼统动作。

- 数量与复杂度匹配，不设强制下限；小功能可只拆几步，大功能先列主干再细分。
- 标注依赖关系，指出**确实**可并行的工作。
- 每个节点写清"交付什么"和"怎样算完成"。
- 不要把简单机械操作包装成里程碑。

### 第 4 步：列出待确认问题

区分优先级：

- **阻塞性问题**：不确认就可能导致需求理解错误、核心设计返工或无法正确开工——优先请用户确认。
- **非阻塞性问题**：可按项目惯例或合理默认推进，不无故阻塞规划——说明默认倾向即可。

每个问题尽量给**候选答案、推荐倾向和简短理由**，便于快速决策。只列真正有价值的问题，不把普通实现细节都升级成必须拍板的决策。

### 第 5 步：分析影响面与风险

说明：涉及模块/接口/数据/配置、对既有功能与共享数据的潜在影响、风险与边界（异常输入、并发、重复操作、外部服务失败、权限、安全等与本功能实际相关的）、需同步的文档、以及哪些只是初步推断仍待检查。没有依据不要断言具体文件一定会被改；避免"注意异常处理"这类空话，要说清风险出现的**具体条件**和**可能后果**。

### 第 6 步：列出测试点

覆盖：主流程、边界与异常（无效输入、空数据、失败响应、超时、重复操作等）、回归风险、以及仅相关时才考虑的非功能验证（权限/安全/性能/兼容）。遵循项目既有测试框架与命名，不假定统一技术栈。

注意区分：**节点完成标准**用于判断某阶段交付物是否达标；**测试点**用于验证功能在正常/异常/边界/回归下是否符合预期。此步骤只规划，不写测试代码。

### 第 7 步：建议 Git 分支名

1. 优先用用户明确提供或项目文档记载的约定。
2. 可用只读查询（如 `git branch -a`）辅助判断命名习惯。
3. 不得为确认规范而创建/切换/删除/重命名分支。
4. 无法核实约定时明确说明，并使用默认：`feature/<short-kebab-name>`。

若项目用 `feat/`、`fix/` 等风格则沿用。分支名简短、kebab-case、能看清功能。只给建议，不创建分支。

## 分析深度

- **轻量**：小型、低风险改动——快速给目标、必要步骤、主要风险、少量测试点、分支名。
- **标准（默认）**：常规新功能——按下方输出格式给全套。
- **深入**：跨模块、涉及数据库迁移/公共接口/安全权限/并发/高风险——额外分析方案权衡、依赖、兼容、回滚策略与更完整验证计划。

可自动判断，也尊重用户指定的深度。**无论何种深度，都不得为填满模板而编造内容。**

## 输出格式

默认按此结构；可随功能规模压缩各板块，但保留核心视角。某板块确实不适用就简要说明，不制造无意义内容。

```text
## 功能：<一句话目标>

### 1. 目标与约束
- 目标：<解决什么问题 / 预期价值>
- 明确约束：<技术栈、兼容要求、明确不做的事>
- 本期范围：<要做什么；必要时注明暂不做什么>
- 假设 / 待检查：<尚未确认的前提，或缺失的项目上下文>

### 2. 关键节点
- [ ] 节点一：<交付物或结果>
  - 完成标准：<可验证的判断依据>
  - 依赖：<前置节点；没有则省略>
- [ ] 节点二：...
- 可并行事项：<确实能并行的；没有则省略>

### 3. 待你确认
- 阻塞性问题：
  - Q1：<问题>？（推荐倾向：<方案及理由>）
- 非阻塞性问题 / 暂定假设：
  - <问题或假设>（默认方案：<方案>）
- 若无需用户确认的问题，明确说明。

### 4. 影响面与风险
- 已确认涉及：<有依据的模块/接口/文件/数据>
- 可能涉及 / 待检查：<尚未核实的影响面>
- 风险与副作用：<具体风险及触发条件>
- 文档同步：<需更新的文档；暂无明显需求可简述>

### 5. 测试点
- 主流程：...
- 边界 / 异常：...
- 回归：...
- 其他必要验证：...（仅适用时列出）

### 6. 建议分支名
- 分支名：<branch-name>
- 依据：<项目既有约定 / 只读查询结果 / 默认建议>
```

功能特别简单时精简条目，但不要为凑格式而填。无法确认的信息标"待检查"或"待确认"，不要把猜测写成事实。

## 完成后的交接

简述当前是否具备开工条件：

- 无阻塞问题：说明推荐方案与主要假设，问用户是否开始实施。
- 有阻塞问题：优先等用户确认；非阻塞项不应阻止其余计划推进。
- 缺项目上下文：只指出下一步最有价值的检查项，不要求用户无差别提供整个项目。

**不自动开始写代码、不改文件、不创建/切换分支、不执行暂存/提交/合并/推送等状态变更。**

## 最终检查

- [ ] 准确表达用户目标与明确约束。
- [ ] 区分了已确认事实 / 假设 / 待检查 / 待用户确认。
- [ ] 只提真正影响设计或开工的问题（能自己查的已先查）。
- [ ] 关键节点有清晰交付物与完成标准。
- [ ] 控制了本期范围，未把可选扩展混入必做任务。
- [ ] 影响面与风险有具体依据，或已标"待检查"。
- [ ] 测试点覆盖相关主流程、边界与回归。
- [ ] 分支名遵循项目约定；无法确认时说明用了默认值。
- [ ] 严格遵守只读边界，未执行任何状态变更。
- [ ] 输出与功能复杂度相称，未为填模板而凑内容。
